# 互操作评估：Cyberdyne-Bridge 能不能适配“市面上所有 MC Agent”？

- **日期**：2026-10-23
- **评估对象**：`~/cyberdyne-bridge`（评估基线 `49511ba`；之后主链有他人提交，写作后 HEAD 已到 `2ef1ab5`，行号可能漂移；结论按基线代码）
- **评估方式**：静态代码审计 + 市面 MC Agent 接口形态对照；**未做**真实第三方 Agent 的 live 互联测试
- **范围**：只评估“脑 ↔ 手”这条协议，以及它作为“其他 Agent 的身体/工具层”时的互操作能力；不改主链

---

## 0. 结论

**不能。至少现在不能，而且“所有”这个目标本身不成立。**

更准确地说：

1. 它现在不是一份**可互操作的协议规范**，而是一份**“一个大脑 ↔ 一只 Mineflayer 手”的私有 RPC 参考实现**。
2. 直接能接的只有仓库里这只手；第三方要接，得先 reverse-engineer 这只手的 2,000 行 JS；要替换大脑，还得读 4,300 行 Python。
3. 对市面其他 MC Agent，最多做到“**写适配器后部分互通**”，做不到“所有”。
4. “所有 MC Agent”至少分成**代码即动作、工具调用、低层 RL、聊天命令、闭源商业**五类动作抽象，再加一类**运行时差异**（Java/Bedrock、vanilla/modded、在线/离线）；动作抽象不在一个层面上，也没有一个人人都实现的 MC Agent 高层协议。

好消息是：你要的“通用”不需要推翻重来。真正缺的是把已经写死在脑子里的契约**搬到线上**：版本/能力协商、请求生命周期、可订阅观测、完成判据契约、多智能体仲裁。这五层补上，才有可能从“我的 Agent 能跑”走到“别人的 Agent 也能接”。

---

## 1. 先把“适配”拆成五层

“适配”不是一个 yes/no，至少分五层：

| 级别 | 含义 | 现在到哪了 |
|---|---|---|
| **P0 同世界** | 能进同一个 Minecraft 世界（版本、认证、Java/Bedrock） | 部分：Java 1.21.1、离线模式、单 bot |
| **P1 同传输** | 能收发同一套字节流（Unix socket / TCP + 一行一条 JSON） | 能：但没规范、没握手、没版本 |
| **P2 同动作** | 认识同一套动作名、参数、语义 | 只认自己这只手的 29 个命令 |
| **P3 同任务** | 对“什么叫完成/失败/可重试”有同一套判据 | 没有：完成判据在脑的任务栈里，不在协议里 |
| **P4 同社会** | 多 Agent 共享一个身体/世界时的身份、租约、仲裁 | 没有：多客户端只是“多个大脑抢一只手” |

**关键区分：两种“接入”不是一回事。**

- **身体模式（推荐）**：外部 Agent 把 Cyberdyne 当成“手/技能层”，上面仍然有任务栈、安全白名单、完成判据。适配器写在上层（MCP / tool schema / 代码 shim）。
- **大脑模式（不推荐）**：外部 Agent 直接替换 `bridge.py`，自己说手侧协议。这样能绕过任务栈，但也必须自己重写安全、完成判据、记忆、重连、探针——而且手侧协议没有请求 ID，多个动作一并发就对不上号。

现在 README 说的“Agent ↔ 物理世界通用协议”（`README.md:43`），更准确的说法是：**一套关于“事实判完成、fail-closed、不静默”的设计原则 + 一个 Minecraft 参考实现**。原则是通用的，线格式不是。

## 2. 协议现状：哪些是协议，哪些只是实现

### 2.1 传输与帧

- 脑是客户端，手是服务端；Unix domain socket，Windows 退化为 `127.0.0.1` TCP（`bridge.py:89-97`、`node/server.js:92-140`）。
- 一行一条 JSON；手侧单行上限 64 KB，超了丢包（`node/server.js:109-120`）。
- 没有 TLS、没有 token、没有连接鉴权；UDS 靠文件权限，TCP 靠 bind 到回环地址。
- 没有握手：手一接上就发 `lastState`（`node/server.js:129-130`），脑默认对面一定是自己认识的 schema。

**结论**：P1 够用，但这是“本地研究环境”的传输，不是“通用协议”的传输。

### 2.2 消息信封：三套字段，没有请求 ID

现在的消息大致是：

```json
{"type":"state","t":1700000000000,"seq":12,"bot":"DeepSeek","pos":[...],"hp":20,...}
{"cmd":"dig","p":[1,2,3]}
{"act":"goto","p":[1,2,3]}
{"type":"event","kind":"cmdResult","cmd":"dig","ok":true,"why":null,"t":...}
{"type":"event","kind":"chat","from":"mintstar","text":"..."}
```

问题不在 JSON，而在**契约没有固定**：

- 动作键既可以是 `cmd`，也可以是 `act`（`node/server.js:1169-1172`）；任务书里写 `act`，M1 动词写 `cmd`。
- 坐标键既可以是 `p`，也可以是 `pos`（`node/server.js:1316-1317`）。
- 回执只有 `cmd` 名字，**没有 `id` / `request_id`**（`node/server.js:1040-1045`）。同一个 `dig` 连发两次，回来两条 `cmdResult`，脑分不清哪条对应哪次。
- `seq` 只在 state 里自增（`node/server.js:855`），脑侧没有任何地方消费它（`bridge.py` 里 grep 不到 `seq` 的使用）。它现在是装饰品，不能做去重/断点续传。
- 没有 `protocol_version`，没有 `mc_version` 协商，没有“手支持哪些动作”的机器可读清单。唯一的“能力”信号是 state 里的 `plugins.pathfinder/body` 两个布尔（`node/server.js:946-949`），它不告诉你 `collect` 在不在、`chest_take` 在不在。

**结论**：这是一套“实现即规范”的私有 RPC。第三方只能读代码，不能靠规范对接。

### 2.3 动作面：其实有三套词汇

| 层 | 词汇 | 数量 | 谁看得见 |
|---|---|---|---|
| LLM 单步 | `follow` / `goto` / `say` / `stop` / `status` / `friend` | 6 | 模型 |
| 任务书 | `走到` / `挖` / `拾` / `放` / `打` / `等` / `说` / `熔炉放料` / `熔炉取成品` / `wait_until` + 车厢扩展（`合成` / `箱子里取` / `往箱子里放` / `collect`） | 10 + 4 | 任务栈 / 翻译器 |
| 手侧 | 内置 15 个（`变了` / `move`/`retreat` / `eat` / `stop` / `scan_environment` / `scan_clear` / `watch_blocks` / `watch_items` / `furnace_watch` / `ping` / `say` / `friend` / `attack` / `mode` / `goto`）+ 身体插件 13 个（`sneak` / `jump` / `jumpattack` / `swimdown` / `dig` / `place` / `craft` / `use` / `furnace_put` / `furnace_take` / `chest_take` / `chest_put` / `递`）+ 能力插件 1 个（`collect`） | 29 | socket 客户端 |

三套词汇之间的映射是隐式的：`走到 → goto`、`挖 → dig`、`放 → place`、`打 → attack/jumpattack`、`说 → say`、`熔炉放料 → furnace_put`……写在 `任务栈._下发` 里（`bridge.py:1941-2020`），没有一张公开的映射表。

更麻烦的是：`follow`、`status`、`look` 是**脑内动作**，手侧根本没有这些命令；`wait_until` 是**任务栈动作**，也不下发。外部 Agent 如果只看手侧命令表，会以为 `follow` 不存在；如果只看 LLM 白名单，会以为 `dig` 不存在。

**结论**：动作面不是“一个协议”，是“三层各自为政的词汇表 + 隐式翻译”。这对自家用没问题，对第三方是灾难。

### 2.4 观测面：快照 + 抽样，不是可订阅的世界模型

`snapshot()` 每帧发的是（`node/server.js:853-974`）：

- 自身：`pos`、`hp`、`food`、`onGround`、`look`、`held`、`durability`、`acting`；
- 附近：`near`（最多 8）、`threats`（最多 4）、`drops`（最多 6）、`players`（全部在线玩家）；
- 背包：`items` 全量物品计数；`foods`、`weapons`；
- 探针：`blocks`（盯的方块 + 身边四格 + 脚下竖列，最多 32 个 watch）、`furnace`（按需）、`watched`；
- 扫描：`scan`（`scan_environment` 的结果，抽样半径 12、步长 2；`scan_radius/scan_step` 在 config 的 `m5` 段）；
- 状态：`stuck_count`、`attacked_by`、`deaths`、`t`、`seq`。

没有的东西：

- **没有像素/截图/POV**；多模态 Agent 拿不到图像。
- **没有完整方块网格**；只有抽样扫描 + 少量探针。外部 Agent 不能按任意坐标查询，只能请求 `scan_environment` 或 `watch_blocks`。
- **没有背包槽位/容器完整内容**；只有物品计数、手持和四件护甲耐久。要做“整理箱子/装备指定槽位”的 Agent 接不了。
- **state 没有增量**；只有整帧快照，外加少量 `event`（chat / spawn / 声呐）。`seq` 不消费，断线重连后无法判断丢了多少帧。
- **没有订阅过滤器**；`watch_*` 是“盯什么”，不是“按频率/条件推送”。

**结论**：这是一套为“自家任务栈”裁剪过的观测面，不是通用的世界模型接口。

### 2.5 完成判据：在脑里，不在协议里

这是最关键的一条。

手侧回执只说明“命令收到了/动作跑了”（`cmdResult`），但任务是否完成由脑的 `任务栈._看完成了没` 判断（`bridge.py:1786-1843`）：

- `挖`：看 `s["blocks"]` 里那一格是不是变成了空气；
- `放`：看那一格是不是变成了期望方块；
- `拾` / `collect`：看 `s["items"]` 里物品数量有没有达到“挖前 + 数量”；
- `打`：看 `s["watched"]` 里对方血量，或 `s["players"]` 里还在不在；
- `走到`：看 `s["pos"]` 的水平距离和高度差；
- `熔炉放料` / `wait_until`：看熔炉读数和条件。

也就是说：**`ok:true` ≠ 完成**。`move` 甚至是在“开始跑”的时候就回执（`node/server.js:1193-1204`）。不同动词的 `ok` 语义不一致：有的是“已受理”，有的是“已执行完”，协议里没有区分。

外部 Agent 要想正确判断完成，必须：

1. 自己实现同样的探针订阅（`watch_blocks` / `watch_items` / `furnace_watch`）；
2. 自己实现同样的完成判据（方块变空气、背包增量、实体消失……）；
3. 自己处理“探针没到货时不算完成”的边界（`bridge.py:1806-1810`）。

这三点都不在协议里。**这是“适配所有 Agent”最大的语义鸿沟**：别人可以学会你的 JSON，但学不会你脑子里的判据。

### 2.6 连接与多智能体：多客户端 ≠ 多 Agent

手侧维护一个 `clients` Set（`node/server.js:96`），所有 state 广播给所有客户端（`node/server.js:151-157`），任何客户端都能发命令（`node/server.js:103-120`），没有 `agent_id`、没有租约、没有“谁说了算”。

后果：

- 两个 Agent 同时接上，都会收到同一份 state，都能对同一个 bot 下命令；后到的命令覆盖先到的，**没有仲裁**。
- 一个 Agent 断线，只要还有别的客户端连着，手不会停动作（`clients.size === 0` 才停，`node/server.js:123-128`）。
- 无人主动问时，事件走“最近来问话的 socket”（`最近出口`，`node/server.js:1633`），不是按 Agent 路由。

README 也诚实写了“没做多人协作、跨 Agent 通信”（`README.md:96`）。所以 P4 是 0，不是“差一点”。

### 2.7 运行环境：Java only，1.21.1，离线模式

- `config.json`：`mc_version = 1.21.1`，`mc_host = 127.0.0.1`，`mc_port = 25565`。
- `node/server.js:175-182`：`mineflayer.createBot({ auth: 'offline', version: cfg.mc_version })`。
- `node/package.json`：`mineflayer ^4.39.0`，`mineflayer-collectblock ^1.6.0`。
- README 明确 Linux only（`README.md:26`）。

这意味着：

- **Bedrock 版 Agent 接不了**（Mineflayer 是 Java 协议）。
- **在线模式/正版验证服务器接不了**（`auth: 'offline'`）。
- **模组方块/物品**没有保证；方块交互表是 1.21.1 原版口径，未知方块会走 fail-closed。
- **跨版本**没有保证；1.21.1 之外的协议字段/方块名/配方可能变。

### 2.8 协议成熟度记分卡

| 维度 | 分数（0–3） | 说明 |
|---|---|---|
| 有正式规范 | 0 | 没有 schema / IDL / 版本号；只有实现和文档 |
| 握手与版本协商 | 0 | 没有 hello/welcome，没有 protocol_version |
| 分帧 | 2 | NDJSON + 64KB 上限，够用 |
| 请求生命周期 | 1 | 有 cmdResult，但没有 id、没有 accepted/completed 区分、没有 cancel |
| 观测契约 | 1 | 快照 + 抽样，无像素、无完整网格、无 delta |
| 完成判据 | 0（作为协议） | 在脑里，不在线上 |
| 能力发现 | 0 | 只有两个插件布尔，没有动作清单/参数 schema |
| 错误模型 | 1 | `ok:false` + 自由文本 `why`，没有稳定错误码 |

> 这张表不是说项目差，而是说：**它是一份很好的“单 Agent 参考实现”，还不是一份“互操作规范”。**

## 3. 市面 MC Agent 分六类，逐一对照

> 下面是“代表”，不是穷举；市场每天都在变。

| 类别 | 代表 | 它怎么动作/观测 | 能直接接吗 | 要接得写什么 | 结论 |
|---|---|---|---|---|---|
| **Mineflayer LLM Agent** | Voyager、Mindcraft、大量自建 bot | JS 代码即动作 / 自己的 JSON 动作层；文本观测 + 背包/附近实体 | **否** | 写“技能 shim”：把它的 `mineBlock/craftItem/goto` 映射到桥的 `dig/craft/goto`；或反过来把桥包成它的一个 action | 同一具身体，不同的大脑接口；适配可行，但不是协议兼容 |
| **MCP MC Agent** | Minecraft MCP server、Bedrock 的 Mc-Agent 等 | MCP tools/resources；每个 server 的 tool schema 各不相同 | **否** | 写 MCP facade：`minecraft_observe` / `minecraft_act` / `minecraft_job` / `minecraft_cancel`，长任务用 job + poll | 最快覆盖“工具调用型” Agent；仍需定义 MC 语义 |
| **RL / 具身环境** | MineRL、MineDojo、MineStudio、Malmo | RGB/体素观测；低层按键/相机/功能动作（MineDojo 8 维 MultiDiscrete；MineRL 字典动作） | **否** | 动作/观测双向适配；把 20 维按键翻译成高层动词，把 JSON 状态渲染成 RGB/体素 | 语义鸿沟最大；只适合做 benchmark 网关，不值得硬接 |
| **脚本/寻路 bot** | Baritone | 聊天命令（`#goto` / `#mine`）；Fabric mod；只有腿和挖 | **否（但互补）** | 把手侧的 `goto` 换成 Baritone 引擎；或把 Baritone 当一个 hand 插件 | 不是 Agent，是“腿”；接它是增强手，不是适配大脑 |
| **闭源商业 / 多智能体实验** | Project Sid 这类 | 私有协议/私有客户端；不公开 wire format | **否** | 只能同服观察、截图、RCON、mod 注入；没有协议级接法 | “所有”里最硬的一类：人家根本没打算让你接 |
| **Bedrock / 主机 / 模组服** | Bedrock Agent、Geyser 服、整合包 | Bedrock 协议 / 模组 API | **否** | 另写一只 Bedrock hand；方块/物品/容器语义都要重做 | 不是协议层能解决的，是运行时层的问题 |

### 3.1 三个具体对接场景

**场景 A：Mindcraft 接进来当第二个“大脑”**

它接上 UDS，能收 state，能发 `{cmd:"goto"}`。然后它发 `{cmd:"dig"}`，收到 `{kind:"cmdResult",cmd:"dig",ok:true}`，以为挖完了；实际上手只是“开始挖/挖了一下”，完成要看后续 `blocks` 探针。它如果再发一条 `dig`，两条回执都只有 `cmd:"dig"`，无法区分。它还会发现 state 里没有它习惯的完整世界视图。**能跑，但会误判。**

**场景 B：Voyager 想写 `await bot.dig(...)`**

桥没有“执行任意 JS”的接口，只有 29 个固定命令；Voyager 的技能库是任意 Mineflayer 代码，不可能全部映射到 29 个动词。可以做一个受限 shim，只支持 `mineBlock/craftItem/placeItem/killMob/exploreUntil` 这些常用技能；超出范围的代码直接拒绝。**这是“部分适配”，不是“所有”。**

**场景 C：MineRL 的策略输出 20 维动作**

桥的状态是 JSON 方块名/坐标/背包计数，不是 RGB；动作是 `dig/goto/craft`，不是按键/相机。要接，得加一个“低层动作 → 高层动词”的翻译器，再做一个“JSON → RGB”的渲染器；两边都会丢信息。**技术上能写，工程上不建议。**

## 4. 为什么“所有”不成立

1. **没有统一的 MC Agent 高层协议。** 最接近的 MCP 只统一了“怎么调用工具”，没有统一“MC 动作叫什么、参数是什么、什么叫完成”。每个 MC MCP server 的 tool 列表都不一样。
2. **动作抽象不在一个层面。** 代码即动作（Voyager）、JSON 工具（MCP）、低层按键（MineRL）、聊天命令（Baritone）——同一句“去砍树”在不同框架里是四种东西。
3. **运行时都不一定一样。** Java vs Bedrock、vanilla vs modded、离线 vs 在线、1.21.1 vs 1.21.11；桥现在只覆盖其中一小格。
4. **闭源 Agent 没有可接的协议。** 你只能同服观察或注入，不能“适配”。
5. **“所有”不可验收。** 市场是开放的、持续变化的；没有一个清单能证明“所有”。工程上应该把它换成“**主流 N 类 + 适配器 SDK + 一致性测试**”。

## 5. 真正要补的五层

### P0-1 握手与能力协商

接上先交换：

```json
{"type":"hello","protocol":"cbp/1.0","role":"brain","agent_id":"mindcraft-1",
 "mc_version":"1.21.1","capabilities":["move","dig","place","craft","chat"],
 "limits":{"max_frame":65536,"max_inflight":4}}
{"type":"welcome","protocol":"cbp/1.0","hand_id":"mineflayer-main",
 "mc_version":"1.21.1","mods":[],
 "actions":[{"op":"dig","args_schema":{"p":"vec3"},"verify":{"type":"block_gone"}},
            {"op":"collect","args_schema":{"item":"string","count":"int"},"verify":{"type":"inventory_delta"}}]}
```

规矩：

- 版本不匹配 → 明确拒绝，不静默降级；
- 动作不在 `actions` 里 → `UNSUPPORTED_OP`，不是“丢包”；
- `mc_version` / `mods` / `auth` 都上桌，别让对面猜。

### P0-2 请求生命周期

每条命令一个 `id`，并且区分“已受理 / 进行中 / 终态”：

```json
{"type":"cmd","v":1,"id":"c-42","op":"dig","args":{"p":[1,2,3]},"deadline_ms":5000,"idempotency_key":"dig:1,2,3:1"}
{"type":"ack","id":"c-42","state":"accepted"}
{"type":"progress","id":"c-42","p":0.4}
{"type":"result","id":"c-42","ok":true,"facts":{"block":"air"},"error_code":null}
{"type":"cancel","id":"c-42"}
```

必须有的错误码（示例）：

`UNSUPPORTED_OP` / `BAD_ARGS` / `NOT_READY` / `TIMEOUT` / `BLOCKED` / `NO_SIGHT` / `OUT_OF_RANGE` / `CONFLICT` / `CANCELLED` / `INTERNAL`

### P0-3 观测契约

- `state` 加 `seq` 的消费方（去重、断线补帧）；
- 支持 `subscribe`：按主题/频率/条件订阅，而不是只能整帧；
- 明确“哪些字段是保证有的，哪些是 best-effort”；
- 如果要接多模态 Agent，另开 `pov`/截图通道，不要塞进 state；
- 保留 `t`（epoch ms）和 `seq`，并规定“单调递增、重连从 0 或续接”的语义。

### P0-4 完成判据契约

每个动作带 `verify`（或 `success_predicate`），让**任何大脑**都能知道什么叫完成：

```json
{"op":"dig","args":{"p":[1,2,3]},"verify":{"type":"block","p":[1,2,3],"equals":"air"}}
{"op":"collect","args":{"item":"oak_log","count":3},"verify":{"type":"inventory_delta","item":"oak_log","delta":3}}
{"op":"goto","args":{"p":[10,64,10],"near":2},"verify":{"type":"position","p":[10,64,10],"near":2}}
```

这正好把你最值钱的那条原则（**完成看事实，不看回执**）从“脑里的代码”升级成“协议里的契约”。

### P0-5 多智能体仲裁

- `agent_id` / `session_id`；
- `lease`：一个身体同一时间只允许一个 writer；读可以共享；
- `cancel` 要能取消“别人的”任务（需要权限）；
- 资源锁：箱子、熔炉、工作台、传送门；
- 聊天命名空间，避免多个 Agent 抢话；
- 冲突策略写清楚：拒绝、排队、还是抢占。

### P1 安全与一致性

- UDS 文件权限 0600；TCP 必须 token；
- `attack` 这类危险动作要单独授权，不能“连上就能打”；
- 审计日志带 `id`，能复盘“谁下的、什么时候、结果如何”；
- wire-level conformance suite：握手、未知动作、重复 id、取消、超时、断线重连、超大帧、双客户端租约。

## 6. 建议的 CBP v1 最小规范

> 下面把这条协议暂称 **CBP（Cyberdyne Bridge Protocol）**；名字不重要，重要的是把契约写死。

不需要一次做完，先冻结一个“够第三方写 hand”的最小集：

1. **传输**：UDS 优先；TCP 仅回环 + token；NDJSON；单行 ≤ 64 KB。
2. **握手**：`hello` / `welcome`；`protocol` 语义化版本；`actions` 清单 + JSON Schema；`limits`。
3. **命令**：`cmd` / `ack` / `progress` / `result` / `cancel`；`id` 必填；`deadline_ms` 必填；`idempotency_key` 可选。
4. **观测**：`state` + `seq` + `t` + `obs_version`；`subscribe` 主题；`delta` 可选。
5. **完成**：每个 action 带 `verify`；`result.facts` 返回可复核的事实。
6. **错误**：稳定错误码 + 人类可读 `why`；未知动作返回 `UNSUPPORTED_OP`，不 disconnect。
7. **多 Agent**：`agent_id`、`lease`、`cancel` 权限。
8. **安全**：token、危险动作白名单、审计。

> 一句话：**把“判据”写进协议，把“实现”留给 hand。**

## 7. 适配器路线（按投入产出排序）

### 第 1 步：MCP facade（覆盖最多“工具调用型” Agent）

- 把桥包成一个 MCP server；
- tools：`minecraft_observe` / `minecraft_act` / `minecraft_job` / `minecraft_cancel` / `minecraft_chat`；
- 长任务返回 `job_id`，用 `minecraft_job` 轮询；
- resources：`minecraft://state`、`minecraft://inventory`、`minecraft://events`；
- 这样 Claude/GPT 等 MCP 客户端至少有了统一的接入面，不需要懂 UDS；能不能干好活仍取决于它自己的规划。

### 第 2 步：Mineflayer 技能 shim（覆盖 Voyager / Mindcraft / 自建 bot）

- 提供一个 `bot` 兼容层，或一个 `skills` 库；
- 只映射桥真正支持的子集：`mineBlock` → `dig`/`collect`，`craftItem` → `craft`，`placeItem` → `place`，`killMob` → `attack`（需授权），`goto` → `goto`；
- 明确写“不支持任意 JS / 不支持任意方块交互”，超出就拒绝；
- 对 Mindcraft 这种多 Agent 框架，先只接一个 Agent，别一上来就抢身体。

### 第 3 步：Hand SDK + conformance suite（让第三方写“手”）

- 给一个最小 hand 模板（Python/Node 各一份）：握手、state 循环、命令分发、回执；
- 给 20 条 wire-level 用例；
- 第三方 hand 只要通过用例，就能接桥；
- 这一步做完，才有可能从“只能接 Mineflayer”走到“能接 Bedrock / 其他模拟器”。

### 第 4 步：Baritone / 寻路（增强手，不是适配 Agent）

- 把 `goto` 换成 Baritone 或 mineflayer-pathfinder；
- 补“路径事件/卡住原因”上报；
- 这不解决“所有 Agent”，但能让现有手更强。

### 第 5 步：RL 网关（只做 benchmark）

- 如果只是想在 MineRL/MineDojo 上评测，不要把桥硬改成 Gym；
- 单独写一个 `gym → CBP` 网关，明确“高层动作/低层动作”的映射和损失；
- 不要宣称“适配”，宣称“可评测”。

## 8. 验收标准：把“所有”换成可测的目标

建议把目标改成下面这组，能验收、能复算：

- [ ] **3 类参考 Agent** 各接一个：一个 Mineflayer LLM（Mindcraft 或 Voyager）、一个 MCP 客户端、一个脚本/RL 网关；
- [ ] **20 条 wire-level 用例**：握手、版本不匹配、未知动作、重复 id、取消、超时、断线重连、超大帧、双客户端租约、完成判据……
- [ ] **2 个 MC 版本**：1.21.1 + 一个相邻版本；明确哪些方块/物品不支持；
- [ ] **1 个第三方 hand**：不读 `bridge.py`，只按 spec 实现，能通过用例；
- [ ] **2 个 Agent 抢一个身体**：lease 生效，不出现命令交错；
- [ ] **0 字节主链改动**：所有适配都在 `外挂/` 或独立进程；
- [ ] **失败可解释**：每个拒绝都有稳定错误码 + 审计 `id`。

做到这些，才可以说“**适配了主流几类**”；“所有”仍然不要写进 README。

## 9. 诚实边界

- 本文是**静态审计**，没有真的让 Mindcraft/Voyager/MineRL 连上来跑；所以“能/不能”是代码层判断，不是实测结论。
- 市面产品只取了代表，不是穷举；闭源产品可能随时改接口。
- 代码行号基于评估基线 `49511ba`；之后主链有他人提交（`2ef1ab5` 起），`bridge.py` / `node/server.js` 已被改动，行号可能漂移，但协议层的结论不变。
- 本文没有改 `bridge.py`、`node/server.js` 或任何车厢；只新增了这份评估。
- 如果主人要的是“**我家这只手能不能被别的 Agent 用**”，答案是“能，但要先写适配器”；如果主人要的是“**所有 Agent 插上就能用**”，答案是“现在不能，而且不该把它当成近期目标”。
