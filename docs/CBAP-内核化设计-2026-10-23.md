## 0. 一句话结论

**方向对，而且比“适配所有 MC Agent”更接近可落地。** 它把适配成本从 **N×M** 降到 **N+M**：
N 个 Agent 只要各写一个薄适配，M 种身体只要各写一个驱动，内核只认一套 ABI。

但四层里现在只有第一层有雏形，后三层还主要是概念；而且“内核”不是比喻，它要付代价：

- 稳定的 ABI（不能今天 `cmd`、明天 `act`）；
- 进程/资源隔离（车厢现在是**在脑进程里 setattr 打补丁**）；
- 可抢占的调度（System 1 必须能打断 System 2）；
- 资源所有权与权限（谁能碰这只手、碰多久）；
- 硬件级安全状态（`SIGKILL` ≠ 机械臂安全）。

**最重要的一句：内核不能认识 `dig` / `craft`。** 这些是 Minecraft 驱动的方言，不是系统调用。内核只认 `read` / `write` / `ioctl` / `poll` / `lease` / `estop` 这些通用动作；`dig` 属于 `mc-driver`。

## 1. 用操作系统的话，把你的四层说清楚

| OS 里的东西 | 你的对应物 | 它该负责 | 它**不该**负责 |
|---|---|---|---|
| **Kernel** | `bridge.py` + 任务栈 + 反射层 + 安全 | 调度、抢占、资源分配、权限、审计、Veto | 认识 Minecraft 方块名/配方/动作 |
| **System Call** | CBAP `read()` / `write()` | 稳定、版本化、可阻塞/非阻塞的 ABI | 直接等于“提交任务”或“规划” |
| **Driver** | Adapter / MC 包 / 机械臂驱动 | 把通用通道翻译成设备方言 | 决定“该不该挖”“该不该打” |
| **Package Manager** | 依赖拉取脚本 | 解析、下载、校验、装环境、回滚 | 在运行时做安全决策 |

四个层混在一起，就会出现现在这种局面：

- 内核里有 `dig` / `craft` / `blocks` / `items`；
- 驱动里有“该不该打”的判断（`朋友` 名单、`攻击` 白名单）；
- 车厢既像内核模块，又像策略插件，还像驱动；
- 依赖靠 `npm install` + shell 脚本，没有包格式。

这不是说现在写得乱，而是说：**四层还没分家**。要内核化，第一步不是加功能，是**划边界**。

## 2. 现状对照：四层各到哪了

| 层 | 你的设想 | 现在有什么 | 缺什么 | 状态 |
|---|---|---|---|---|
| **Kernel** | 调度 + 安全 + Veto | `bridge.py` 里有反射层、任务栈、心跳、记忆、LLM、socket 客户端；`tools/看护.py` 能 SIGTERM 手和脑 | 独立内核进程；调度器/优先级/截止时间；资源所有权；权限；设备管理器；可抢占 | **雏形** |
| **CBAP** | `read()` / `write()` 系统调用 | UDS/TCP + 一行一条 JSON；`cmd`/`act`；`state` / `cmdResult` | 版本化 ABI；fd/handle；`open/close/ioctl/poll`；errno；背压；SDK/IDL | **私有 RPC** |
| **Driver** | 自动生成适配器、热插拔 | `node/plugins/body` + `node/plugins/能力`；`外挂/` 26 节车厢 | 设备描述符；驱动 ABI；驱动注册表；热插拔；一致性测试；自动生成 | **部分** |
| **Package Manager** | `apt install` 式拉依赖 | `npm install`、`tools/启动*.sh`、`外挂/启动列车.sh` | 包格式；仓库索引；lockfile；校验和；沙箱；回滚；按项目隔离 | **没有** |

### 2.1 为什么说车厢不是驱动

`外挂/车钩.py` 的做法是：读 `manifest.json`，`import` 补丁，然后 **`setattr` 覆盖 `bridge` 里的类属性**；换轨时全部卸下再按顺序挂上；宪法体检检查“顶层对象身份没变”。

这很像**内核模块**：在同一个地址空间里挂钩子、改行为、加载/卸载。它**不是驱动**：

- 驱动面对的是“设备”，车厢面对的是“大脑里的类”；
- 驱动有设备描述符/通道/单位/安全边界，车厢只有 `补丁点` 名字；
- 驱动可以独立进程/独立语言，车厢必须是 Python 且和主链同进程；
- 驱动坏了不能带崩内核，车厢坏了（一个 `setattr` 写错）可以带崩整个脑。

所以“26 节车厢”证明的是**内核模块热插拔**，不是**驱动热插拔**。这两个能力都值得保留，但要分开放。

### 2.2 为什么说现在还不是内核

严格意义上的内核至少要有：

1. **特权边界**：用户态 Agent 不能直接改内核内存；现在任何 socket 客户端都能对同一个 bot 下命令。
2. **资源所有权**：内核决定谁在什么时候用哪只手；现在多个客户端是“谁后发谁赢”。
3. **可抢占调度**：System 1 的保命动作要能打断 System 2 的规划；现在是同一个 Python 循环里的顺序执行，LLM/网络/文件 I/O 可能把循环卡住。
4. **故障隔离**：一个驱动/Agent 崩了，内核还在；现在车厢是 in-process patch，补丁抛异常可以带走主循环（虽然有兜底）。
5. **稳定 ABI**：驱动/Agent 按头文件写，不按“读 bridge.py 猜”。

这五条不需要一次全做到，但**如果一条都不做，叫“内核”就只是修辞**。更诚实的叫法是 **Agent Runtime（代理运行时）**；等这五条到位，再叫内核。

## 3. 六个必须先拍板的设计判断

### 判断 1：内核必须与 Minecraft 解耦

内核的 syscall 里不能出现：

- `dig` / `place` / `craft` / `attack` / `jumpattack`；
- `blocks` / `items` / `furnace` / `hp` / `food`；
- 方块名、物品名、配方、坐标语义。

这些都应该在 `mc-driver` 里。内核只看到：

- 一个 **device**（`mc://bot/DeepSeek`）；
- 若干 **channel**（`body` / `world` / `inventory` / `chat`）；
- **frame**（带 schema 的二进制/JSON 载荷）；
- **capability**（这个 device 能做什么）；
- **lease**（谁独占这只手）；
- **estop**（安全状态）。

MC 驱动把 `world.dig(p)` 翻译成 mineflayer 的 `bot.dig`；机械臂驱动把 `arm.move(pose)` 翻译成关节轨迹。内核不关心。

### 判断 2：`read()` / `write()` 不够，至少还要 `open/close/ioctl/poll/lease/estop`

`read`/`write` 是最小集，但真实设备需要：

| 调用 | 为什么需要 |
|---|---|
| `open(device, mode)` | 拿到 fd/handle；区分只读/读写/独占 |
| `close(fd)` | 释放租约、停动作、清资源 |
| `read(fd, buf, timeout)` | 读状态；要能阻塞/非阻塞、超时、返回 `EAGAIN` |
| `write(fd, buf, deadline)` | 下发动作；要能背压、拒绝、取消 |
| `ioctl(fd, op, args)` | 设备特有操作：MC 的 `scan/craft/watch`；机械臂的 `gripper`；狗的 `gait` |
| `poll(fds, timeout)` | 等事件：聊天、受伤、到达、错误、急停 |
| `lease(fd, ttl)` | 独占身体；多 Agent 时必须有 |
| `estop(fd)` | 安全状态；不是普通 `write("stop")` |
| `stat(fd)` | 设备健康、能力、限额、版本 |

只有 `read/write` 的协议，最后一定会长出一堆“特殊 JSON 字段”来补 `ioctl` 的活——现在的 `cmd`/`act` 就是证据。

### 判断 3：Veto 必须是“安全状态”，不是“杀进程”

MC 里杀 Node 进程 ≈ 断开连接，bot 会停下，勉强算安全。
机械臂/四足不一样：

- 杀进程可能让驱动器保持最后一次力矩/速度指令；
- 四足杀进程可能直接摔倒；
- 机械臂杀进程可能夹着东西不放。

所以 Veto 要分三层：

1. **驱动级 `estop()`**：刹车、断力矩、回安全位、保持站立/阻尼；
2. **硬件看门狗**：驱动/内核心跳停了，硬件自己进安全状态；
3. **进程级 SIGKILL**：最后手段，不是第一手段。

现在的 `tools/看护.py` 是 `os.kill(pid, 15)`（SIGTERM），手侧收到后 `停动作 + bot.quit()`；这对 MC 是合理的，对机器人不够。**内核化的安全设计，必须把“安全状态”定义成驱动契约的一部分。**

### 判断 4：System 1 / System 2 需要“可抢占”，不是“写在同一个循环里”

现在 `bridge.py` 的主循环大致是：

```
收消息 →（聊天可能先问 LLM）→ 叙事 → 反射层（保命优先）→ 任务栈
```

反射层确实排在任务栈前面，但它是**协作式**的：如果 LLM 调用、文件写入、RCON、扫描卡住，反射层这一拍就进不来。项目里有超时、限流、看护，但这些是“补救”，不是“抢占”。

内核化要明确：

- System 1：硬截止时间（比如 50ms），最高优先级，可打断 System 2；
- System 2：可中断、可取消、可降级；LLM 调用必须在独立线程/进程，不能占住控制循环；
- 调度器：每个 Agent/任务有配额、优先级、截止时间；
- 看门狗：System 1 超时 → 记录 → `estop`。

如果暂时做不到抢占，至少要把 **LLM/网络 I/O 从控制循环里挪出去**，否则“0ms 反射弧”会被一次 API 超时打穿。

### 判断 5：自动适配需要“描述符 + 一致性测试”，不能靠猜代码

USB 能做到热插拔，不是因为它会读心，而是因为设备会自描述：

- VID/PID、设备类、端点、速率、电源；
- 主机有对应的**类驱动**；
- 枚举失败就拒绝，不会“猜一个配置”。

你的“MC 包自动生成适配器”要成立，至少要有：

1. **设备描述符**：`device.json`——设备类型、通道、能力、单位、坐标帧、限额、安全状态；
2. **动作映射**：`mapping.yaml/json`——通用 op 到设备方言的映射；
3. **一致性测试**：连接、读状态、下发、完成判据、超时、急停、断线重连；
4. **代码生成器**：从描述符生成 SDK 骨架/序列化代码；
5. **人工补齐**：语义、安全边界、完成判据不能自动猜。

能自动生成的是**骨架和管道**，不是**语义**。这一点必须写清楚，否则“自动适配”会变成“自动猜错”。

### 判断 6：包管理器不是“一个 sudo 脚本”

`apt install` 能成立，是因为有：

- 仓库索引、版本、依赖求解；
- 签名/校验和；
- 安装脚本沙箱；
- 锁文件、回滚；
- 系统级权限模型。

“别人拉项目，跑我的脚本，环境自动配好”现在只是 **bootstrap 脚本**，不是包管理器。要做，至少要有：

- `cbap-package.json`：名字、版本、类型、CBAP 版本、入口、依赖、校验和、权限；
- `cbap.lock`：锁定版本/哈希；
- 仓库索引：`cbap install mc-driver@1.0`；
- 按项目隔离的环境（`uv` / `npm` / venv），**不要 sudo**；
- 安装后跑一致性测试；
- 失败回滚。

可以站在 `uv` / `npm` / `cargo` 上，不必自己造下载器；但**包格式和信任链**必须自己定。

## 4. CBAP：两套 ABI，不要混成一套

### 4.1 CBAP-U：Agent → Kernel（系统调用）

面向 Java/Node/Python Agent：

```
fd = cbap_open("mc://bot/DeepSeek", CBAP_RDWR | CBAP_EXCLUSIVE)
cbap_read(fd, &frame, timeout_ms)
cbap_write(fd, &frame, deadline_ms)
cbap_ioctl(fd, CBAP_IOC_SCAN, &args)
cbap_poll(&fds, n, timeout_ms)
cbap_lease(fd, ttl_ms)
cbap_estop(fd)
cbap_close(fd)
```

语义要点：

- `read/write` 是**消息边界**，不是字节流；一条 frame 要么完整，要么 `EAGAIN`；
- `write` 要返回 `accepted / completed` 两段，或者返回 `id` 让 Agent `poll` 终态；
- 每个调用带 `deadline_ms`；超时返回 `ETIMEDOUT`；
- 每个错误有稳定 errno（见 4.3）；
- `open` 带权限：只读、读写、独占；没有权限就 `EACCES`；
- `lease` 是写租约：同一 device 同时只有一个 writer；读可以共享；
- `estop` 不受租约限制，任何人/内核都可以触发（安全优先）。

### 4.2 CBAP-D：Kernel → Driver（驱动 ABI）

面向 MC 驱动、机械臂驱动、四足驱动：

```
describe() -> device descriptor
open(channel, mode) -> handle
read(handle, &frame, timeout_ms)
write(handle, &frame, deadline_ms)
ioctl(handle, op, args)
poll(handles, timeout_ms)
estop() -> safe_state
watchdog(heartbeat_ms)
health() -> {ok, detail}
```

驱动描述符示例（MC）：

```json
{
  "device_id": "mc://bot/DeepSeek",
  "type": "minecraft-java",
  "cbap": "1.0",
  "mc_version": "1.21.1",
  "channels": {
    "body":      {"read": ["pose", "hp", "food", "on_ground"], "write": ["move", "look", "jump", "sneak"]},
    "world":     {"read": ["scan", "blocks"], "write": ["dig", "place"], "ioctl": ["scan", "watch"]},
    "inventory": {"read": ["items", "durability"], "write": ["craft", "equip", "drop"]},
    "chat":      {"read": ["chat"], "write": ["say"]}
  },
  "limits": {"max_frame": 65536, "max_inflight": 4, "max_speed": 1.0},
  "safety": {"estop": "stop+quit", "watchdog_ms": 5000}
}
```

驱动描述符示例（机械臂）：

```json
{
  "device_id": "robot://arm0",
  "type": "robot-arm",
  "cbap": "1.0",
  "channels": {
    "joints":  {"read": ["q", "dq", "tau"], "write": ["trajectory"]},
    "gripper": {"read": ["width", "force"], "write": ["grip", "release"]},
    "camera":  {"read": ["rgb", "depth"]}
  },
  "limits": {"max_velocity": 0.5, "max_force": 40, "workspace": [[...]]},
  "safety": {"estop": "brake+torque_off", "watchdog_ms": 100}

```


### 4.3 Frame 与 errno

Frame 头建议：

```
magic(4) | version(2) | type(2) | flags(2) | reserved(2) | len(4)
seq(8) | t_mono(8) | t_epoch(8) | id(16) | payload(len)
```

- `t_mono` 用于本机判据，`t_epoch` 用于跨进程/日志；
- `id` 是请求 ID，回执必须带回；
- `flags` 区分 `REQUEST / RESPONSE / EVENT / CANCEL`；
- payload 用 JSON（易调试）或 CBOR（省带宽）；机器人高频率用共享内存/ROS 2，不要硬塞 JSON。

errno 建议：

`EACCES` / `ENODEV` / `EBUSY` / `EAGAIN` / `ETIMEDOUT` / `EINVAL` / `ENOTSUP` / `EIO` / `ECANCELED` / `ESAFETY`

对应人类可读 `why`，但**程序只认 errno**。

### 4.4 `read/write` 不是“任务 API”

如果 `write()` 只能下发 `dig` 这种原子动作，那么“用 System 2 规划”就落到了 Agent 自己身上，内核只剩反射。
如果 `write()` 能提交“去砍一棵树”这种任务，那它就不是 syscall，而是 **task API**。

建议分两层：

- **syscall 层**：`read/write/ioctl/poll`，原子、可组合；
- **task 层**：`submit(task)` / `status(task_id)` / `cancel(task_id)`，由内核的 System 2 负责任务栈、完成判据、重试。

Agent 可以只用 syscall（自己规划），也可以只用 task（把规划交给内核）。**不要用同一个 `write` 同时表达两种语义。**

### 4.5 能力本体：不要假设所有身体都有 `dig`

内核不能把 `dig` 当成通用动作。不同身体的能力不一样：

| 能力 | MC bot | 机械臂 | 四足 |
|---|---|---|---|
| `locomotion`（移动） | 有 | 通常没有 | 有 |
| `manipulation`（抓/放/挖） | 有（dig/place） | 有（gripper） | 通常没有 |
| `vision` | 有（方块扫描，不是 RGB） | 有（相机） | 有（相机） |
| `inventory` | 有 | 可能没有 | 没有 |
| `chat` | 有 | 没有 | 没有 |
| `crafting` | 有 | 没有 | 没有 |

所以内核的规划器应该按 **capability** 选技能，而不是硬编码动作：

```json
{"skill":"break_block","requires":["manipulation","vision"],"args":{"p":"vec3"},
 "preconditions":[{"type":"block_exists","p":"$args.p"}],
 "effects":[{"type":"block_gone","p":"$args.p"}],
 "verify":{"type":"block","p":"$args.p","equals":"air"}}
```

MC 驱动提供 `break_block`；机械臂驱动提供 `grasp` / `place`；四足驱动提供 `move_to`。LLM 看到的技能清单来自内核的 capability registry，不是一张写死的 `dig/craft` 表。

### 4.6 “通道蛋白”到底是什么

“通道蛋白”可以保留这个比喻，但要落成四个必须同时匹配的东西：

1. **传输绑定**：UDS / TCP / 共享内存 / 串口 / CAN / ROS 2 / DDS；
2. **分帧与编码**：长度前缀 / NDJSON / CBOR / Protobuf / FlatBuffers；
3. **schema 版本**：`cbap/1.0` + 每个 payload 的 schema 版本；
4. **认证与能力**：token / capability / lease。

四个里任何一个对不上，数据流就不通。所以内核要有 **transport binding** 和 **schema registry**，不能把 UDS + JSON 写死。MC 用 UDS 够了；机械臂/四足可能必须上 ROS 2 或共享内存。

## 5. 内核该有哪些组件

```
┌────────────────────────────────────────────────────┐
│ CBAP-U（Agent 系统调用）                            │
├────────────────────────────────────────────────────┤
│ Syscall dispatcher                                  │
│  - 参数校验 / 权限 / 限流 / 审计 / 超时              │
├───────────────┬────────────────┬───────────────────┤
│ Scheduler     │ Safety          │ Device Manager     │
│  S1 反射       │  fail-closed    │  registry          │
│  S2 规划       │  watchdog       │  hotplug           │
│  配额/租约     │  estop          │  lease/health      │
├───────────────┴────────────────┴───────────────────┤
│ Task/Memory/Audit                                   │
│  task stack / checkpoints / completion / trace      │
├────────────────────────────────────────────────────┤
│ CBAP-D（Driver ABI）                                │
└────────────────────────────────────────────────────┘
```

关键点：

- **内核小**：MC 的方块/配方/动作全在驱动；
- **调度器**：S1 硬截止时间，S2 可中断；每个 Agent 有 CPU/Token/动作配额；
- **安全**：策略引擎 + 看门狗 + 驱动 `estop`；Veto 记录原因、触发源、快照；
- **设备管理器**：设备注册、能力查询、租约、热插拔、健康检查；
- **任务/记忆**：任务栈是内核服务，不是 Agent 私有；
- **审计**：每次 syscall 一条结构化记录，带 `id`、`agent_id`、`device_id`、`op`、`result`、`latency`；
- **模块加载器**：车厢作为“内核模块”加载，但要有版本化 hook ABI；不可信模块不放内核态。

## 6. MC 驱动怎么从现在的代码拆出来

现在的 `bridge.py` 是“内核 + MC 应用 + Agent 运行时”的混合物。拆法：

| 现在 | 拆到哪 | 说明 |
|---|---|---|
| `接线口` / socket 收发 | `kernel/transport/` | CBAP-U 的传输绑定 |
| 反射层 / 任务栈 / 心跳 / 记忆 | `kernel/` | 调度、安全、任务、记忆 |
| `指令层` / `翻译器` / LLM | `agents/` 或 `kernel/services/` | 既可以当内核服务，也可以当第一个 Agent |
| `_看完成了没` / 探针 | `kernel/task/` + `drivers/mc/verify` | 通用完成判据在内核；MC 判据在驱动 |
| `node/server.js` | `drivers/mc/` | mineflayer 驱动 |
| `node/plugins/body` / `能力` | `drivers/mc/` | 驱动内部插件 |
| `外挂/` 车厢 | `modules/` | 内核模块/策略，不是驱动 |
| `tools/` | `cli/` + `ops/` | 运维 CLI，不是内核 |
| `config.json` | `kernel/config` + `drivers/mc/config` | 分层配置 |

第一步不要重写，先**包一层**：

- `kernel` 仍然 import 现在的 `bridge.py` 作为 `legacy_runtime`；
- `mc-driver` 仍然用现在的 `node/server.js`；
- CBAP-U 先做“翻译层”，把 `read/write` 映射到现有 `state`/`cmd`；
- 行为不变，测试全绿，再逐步搬家。

这样“主链零改动”仍然成立；等新路径稳定，再切主链。

## 7. 自动适配/热插拔的真实流程

### 7.1 驱动包长什么样

```
mc-driver/
├── cbap-package.json      # 包元数据、CBAP 版本、权限、依赖
├── device.json            # 设备描述符：通道/能力/限额/安全
├── mapping.json           # 通用 op → 设备方言
├── src/                   # 驱动实现
├── conformance/           # 20 条一致性用例
└── README.md
```

`mapping.json` 示例：

```json
{
  "ops": {
    "move":  {"target": "body.move",  "args": {"dir": "vec2", "ms": "int"}},
    "dig":   {"target": "world.dig",  "args": {"p": "vec3"}},
    "place": {"target": "world.place","args": {"p": "vec3", "item": "string"}},
    "say":   {"target": "chat.say",   "args": {"text": "string"}}
  },
  "verify": {
    "dig":   {"type": "block_gone", "p": "$args.p"},
    "place": {"type": "block_is",  "p": "$args.p", "equals": "$args.item"},
    "move":  {"type": "position",  "near": "$args.p", "radius": 2}
  }
}
```

### 7.2 自动生成能做什么、不能做什么

| 能自动生成 | 不能自动生成 |
|---|---|
| 传输绑定、帧编解码、SDK 骨架 | 动作语义（`dig` 到底怎么挖） |
| 命令分发、错误映射、日志 | 完成判据（方块变空气才算挖到） |
| 状态轮询、心跳、重连 | 安全边界（最大速度/力/工作空间） |
| 一致性测试骨架 | 坐标帧/单位换算 |
| 权限声明模板 | 多人/多 Agent 冲突策略 |

“MC 包自动生成适配器”可以做到：读 `device.json` + `mapping.json`，生成一个能连上、能收发、能跑一致性测试的骨架；但 `dig` 的前置条件、完成判据、失败恢复，仍然要人（或另一个 Agent）写。

### 7.3 热插拔流程

```
cbap driver init mc-driver       # 生成骨架 + device.json 模板
cbap driver test mc-driver       # 连接、读状态、下发、完成、超时、estop
cbap driver install mc-driver    # 注册到 device manager
cbap device list                 # 看到 mc://bot/DeepSeek
cbap device probe mc://...       # 热插拔探测
cbap device remove mc://...      # 卸载，先 estop 再关
```

一致性测试至少 20 条：

1. 握手/版本匹配
2. 未知 op → `ENOTSUP`
3. 参数缺失 → `EINVAL`
4. 只读 fd 写入 → `EACCES`
5. 重复 `id` → 幂等/`EBUSY`
6. 超时 → `ETIMEDOUT`
7. 取消 → `ECANCELED`
8. 断线重连 → 状态续接
9. 超大帧 → 拒绝
10. 背压 → `EAGAIN`
11. 双 writer → 租约冲突
12. 租约过期 → 自动释放
13. `estop` → 安全状态
14. 看门狗超时 → 安全状态
15. 完成判据 → 事实
16. 失败重试 → 不重复副作用
17. 时钟偏差 → 不误判
18. 权限不足 → `EACCES`
19. 设备掉线 → `ENODEV`
20. 驱动崩溃 → 内核存活

## 8. 包管理器：别造 `sudo apt`，造 `cbap install`

### 8.1 包元数据

```json
{
  "name": "mc-driver",
  "version": "1.0.0",
  "type": "driver",
  "cbap": "^1.0",
  "platform": ["linux-x86_64"],
  "entry": "src/main.py",
  "deps": {"python": ">=3.11", "mineflayer": "^4.39.0"},
  "checksums": {"src/main.py": "sha256:..."},
  "permissions": ["device:mc://*", "net:127.0.0.1"],
  "conformance": "conformance/",
  "post_install": "scripts/post_install.py"
}
```

### 8.2 安装流程

```
cbap install mc-driver@1.0.0
  → 读仓库索引
  → 解析依赖（uv/npm）
  → 下载 + 校验和/签名
  → 建项目隔离环境（不 sudo）
  → 跑 conformance
  → 注册到 device manager
  → 写 cbap.lock
```

失败 → 回滚到上一个 lock；不把半装状态留给运行时。

### 8.3 为什么不要 sudo

- Agent 的依赖是**项目级**的，不是系统级的；
- `sudo` 脚本是供应链攻击的入口；
- 机器人/实验室环境更需要可复现、可回滚；
- 用 `uv` / `npm` / venv 做隔离，`cbap` 只做编排和校验。

## 9. 迁移路线（不改主链）

### Phase 0：冻结 CBAP v1（先做这个，不写业务代码）

- 写 `spec/cbap-v1.md` + `schema/*.json`；
- 定 frame、errno、op 名、`device.json`、`mapping.json`；
- 不写代码，先让 Java/Node/Python 三方都能读懂。

### Phase 1：包一层，不搬家

- `kernel/` 里放一个 `legacy_runtime` 适配器，import 现有 `bridge.py`；
- `drivers/mc/` 里放一个 `legacy_hand` 适配器，连现有 `node/server.js`；
- CBAP-U 先做 `read/write/poll` 三个调用，映射到 `state`/`cmd`；
- 当前脑作为第一个 Agent，通过 CBAP-U 调自己；
- 全部现有测试保持绿。

### Phase 2：驱动 SDK + 一致性测试

- 写 `drivers/sdk/python` 和 `drivers/sdk/node`；
- 把 `mc-driver` 从 `legacy_hand` 迁到真驱动；
- 写一个 **假驱动**（模拟机械臂/四足）证明热插拔；
- 20 条 conformance 跑通。

### Phase 3：包管理器

- `cbap-package.json` / `cbap.lock` / 仓库索引；
- `cbap install/list/doctor/rollback`；
- 用 `uv`/`npm` 做依赖，不 sudo；
- 安装后自动 conformance。

### Phase 4：真硬件安全

- 驱动 `estop` + 硬件看门狗；
- 实时控制环用 C++/Rust/ROS 2，不要用 Python/JSON 跑 1kHz；
- 安全边界/工作空间/力矩限制；
- 失效分析（FMEA）和急停测试。

## 10. 那“所有 MC Agent”呢？

**CBAP 不会让所有 MC Agent 自动兼容。** 它做的是：

- 把“每个 Agent × 每种身体”的适配从 **N×M** 降到 **N+M**；
- 让适配器可复用、可测试、可版本化；
- 让新身体/新 Agent 的接入成本从“读 4,300 行 Python”降到“按 spec 写驱动”。

仍然需要适配的：

- **Voyager / Mindcraft**：代码即动作/自有动作层 → 写技能 shim 或 SDK 适配；
- **MCP Agent**：写 MCP facade；
- **MineRL / MineDojo**：低层 RGB/按键 → 写 gateway，且会丢语义；
- **Bedrock**：另写 Bedrock driver；
- **闭源**：没有公开协议，仍然只能同服观察/注入。

所以目标应该写成：

> **CBAP 让“任何能调用 SDK 的 Agent”接入；用驱动覆盖“主流身体”；用一致性测试保证质量。**
>
> 不是“所有 Agent 插上就能用”。

## 11. 风险与边界

1. **内核膨胀**：把 MC 的 `dig/craft` 塞进内核，就会变成“MC 专用内核”，再也接不了机械臂。
2. **Python 实时性**：Python + GIL + JSON 不适合 1kHz 控制环；内核可以监督，实时控制要下放到驱动/RT 线程。
3. **车厢隔离**：`setattr` 补丁是 in-process，一个坏补丁可以带崩内核；可信模块才放内核态，不可信 Agent 放用户态。
4. **安全认证**：真机器人要急停、看门狗、力矩限制、FMEA；软件 Veto 不是安全认证。
5. **包供应链**：签名、校验和、权限、沙箱；不要执行陌生 `post_install` 的 sudo。
6. **“内核”是承诺**：如果暂时做不到隔离/抢占/ABI，就叫“Agent Runtime”；等做到再叫内核，别让名字跑在实现前面。

---

## 12. 结论

- 你的四层抽象是**对的**，而且比“适配所有 MC Agent”更有工程价值：它是 **N+M** 的解法。
- 但现在只有 **Kernel 雏形**；CBAP 还是私有 RPC，Driver 还是身体插件+车厢，Package Manager 还是没有。
- 第一步不是加功能，是**划边界 + 冻 ABI**：内核不认识 `dig`，驱动不认识“该不该打”，包管理器不做运行时决策。
- 做完之后，你可以诚实地说：**“CBAP 让主流 Agent 通过 SDK/驱动接入”**；仍然不能说“所有”。

> 一句话：**内核化不是把现在的桥改个名字，而是把“判据、权限、资源、安全状态”从实现里抽出来，变成别人可以依赖的契约。**
